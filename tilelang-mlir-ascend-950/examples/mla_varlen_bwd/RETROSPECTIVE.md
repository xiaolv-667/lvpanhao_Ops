### Transferable Lessons（可迁移教训）

- 集成 harness 算子前，先读 Stage 3 产物每个工厂的签名与函数尾：若函数体尾是 `tilelang.compile(...)`（一级工厂，返回已编译程序），wrapper 里对它的二次 `factory(block_n, block_m, num_stages)` 调用必然把 tiling 实参当成输入张量喂进去，报 `Kernel expected N inputs, but M are provided`；此时修 `_compile` 与 `default_config`（置 `{}`），不要动 kernel。
- 带 `out_idx` 的工厂按「入参个数 = 签名实参数，出参个数 = `len(out_idx)`」调用（如 `out_idx=[2]` 的两入一出一律 `out = prep(a, b)`）；无 `out_idx` 的工厂必须把全部形参（含 in-out 累加器）都显式传满，且 in-out 累加器需 host 侧预清零。
- 一次调用启动多个 kernel 的 op，`report` 的 benchmark 会因 `msprof --kernel-name` 无法覆盖整调用而 4/4 回退 events（`benchmark_passed=false` 但 `benchmark_failed=0`、`invalid_profile_count=0`）：这是**口径**问题而非精度/功能失败，`status=partial` + 正确性通过即可判完成，但数值只能当 op-wall 用时，不可用于单 kernel 归因。
- 同一 roofline FLOPs 的两个 workload 若实测延迟差一个数量级，优先怀疑数据搬运/负载均衡或计时口径，而不是算力；把它作为负面发现带数字交给性能阶段，不要在集成阶段改 kernel。

### Transferable Lessons（可迁移教训）

- 「grid 触顶 / head-slab 静默」这类修复**不能靠既有 pytest 全绿验收**：本包的 12 个用例没有 H=128 的 8x4k 形状，修复前后都 12/12。重新集成时必须补一次「目标形状的真实 op 调用 + 逐 request/逐 head 非零」与 plan 行核对（`launches*max_grid <= 65535`、`blocks == useful`、`idle == 0`）。
- 判定多 kernel/多 launch op 的性能修复是否生效，只看 `t_op_us`（或 `msprof.t_op_breakdown` 之和）；`latency_us` 与 `result.tflops` 是「各 op 样本中位数」口径，会显示为单次 launch 的量级，不能用它判回退或达标。
- 编译期由运行期形状推导出的常量（如 head slab、tile 数）必须进入程序缓存键，并在 build 后用「重算 plan == 编译产物」断言兜底，否则跨形状复用会静默改变 launch 语义。
- 重新集成一个「已手工修好 wrapper」的算子，验收前提是脚本输出 `wrapper_rewritten: false`（改写会覆盖多 launch 逻辑）；随后直接读 wrapper 的 `_run` 区段确认 `dq_acc` 只清一次、`land` 在所有 slab 之后、`h_off` 为 int32 且按 launch 切片。

### Transferable Lessons（可迁移教训）

- 重跑集成时，「脚本 `smoke-ok` + `wrapper_rewritten: false`」不等于 wrapper 与产物契约一致：产物重设计后先读 `factory_config()` 的键集与 `build_kernel` 签名，再对照 wrapper 调用点；冒烟只验证 import。
- 设计文档/开发日志里的百分比要区分口径：msprof `aic_cube_ratio`（pipe 占用）与 harness `MFU`（roofline FLOPs / cube 峰）是同一测量的两种分母，把前者当后者会误判「重集成后性能掉了 2 个点」。
- 改了 tile 尺寸就要重算 launch 拓扑；验收看 `blocks == useful`、`idle == 0`、`launches * max_grid <= 65535` 三个不变量，不要与旧 `block_n` 下的 grid 绝对值比较。
- 多 launch op 的非静默检查是可复用的低成本门禁：`gen_inputs()` + 逐 request/逐 head `count_nonzero`，能在 1 分钟内否掉「grid 截断/head 丢失」这类 pytest 覆盖不到的静默错误。

### Transferable Lessons（可迁移教训）

- **「wrapper 未被覆盖」≠「wrapper 指对产物」**：`wrapper_rewritten: false` 只说明脚本没动它，不说明它指向本次集成的 kernel。Stage 3 换代后必须先读 wrapper 的**非注释** import 行；本次若漏掉这一步，A5 的 −32% 会被报成 0，且所有验收项（12/12、invalid=0、MFU 数字"合理"）都仍然会通过——这是**无声**的测量错误，比编译失败危险。
- **判「该激活哪个源」看时间线，不看名字**：`.task_timeline.jsonl` 里该 func 最后事件是 `DEV_LOOP done` ⇒ 新产物是 Stage 3 baseline；`perf_opt/{func}.py` 的 mtime 早于 `DESIGN.md` 重写 ⇒ 它是上一代。两个信号 + wrapper 生效行三者一致再跑 report。
- **设计换代会让旧 Stage 4 drop-in 语义失效，且失效是静默的**：v4 的 `_STAGES=3` 是调度提示，v5 的 `num_stages==2` 是「两个静态半体」的契约（`build_kernel` 里显式 `ValueError` 兜底）。旧 drop-in 仍能构建、仍能跑、只是慢 —— 所以「能跑」不能当作「可采纳」。
- **换代集成的一次过序列**（本次 0 attempt，全程约 55 min，其中 report 约 45 min）：`integrate_kernel.py` → 6 产物 `cmp` → 读 active 源（必要时切块）→ `inspect.signature` 绑定 + `factory_config()` 断言（`num_stages==2`）→ `plan_launch` 三不变量（`blocks==useful`、`idle==0`、`launches*max_grid<=65535`）→ `pytest`（2.3 min，最便宜的端到端门禁）→ 8x4k 非静默 → report。把 report 放最后，可避免用 45 min 的算力去发现一个 2 min 就能暴露的问题。
- **集成复测与 dev 实测的偏差判据**：本次 8x4k 138.35 vs 139.5（−0.8%）、mixed 441.70 vs 440.2（+0.3%）、kimi 140.30 vs 140.4（−0.1%），均在 ±1% 内 ⇒ 集成本身无额外开销；超过 1% 才值得怀疑 wrapper 走了别的源或 slab 变了。
- 报告表 `Latency` 列对多 launch op 仍是单次样本口径（本次 8x4k 32.9 ms / mixed 108.6 ms，而 `t_op_us` 是 138.4 / 441.7 ms），继续只认 `t_op_us` / `msprof.t_op_breakdown` 之和。
