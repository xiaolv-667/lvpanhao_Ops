### Transferable Lessons（可迁移教训）

- **共享测试文件下 `run --op X` 会跑整文件**：先把 `run.json.correctness.cases[*].name` 按 op 前缀分组（本任务 Fwd 13 / Bwd 17 / Decode 16 = 46），失败才谈归因；`report.md` 的 per-op 用例数是「未标注 op 的用例归给唯一被请求算子」的产物（28 vs 13），不要据此判断本算子覆盖了多少用例。
- **benchmark 是否有效看 `performance.cases[*].profiler_valid`**，不看 pytest bench 用例的 outcome：本轮 10/10 bench 用例 `passed`，仍有 4 条 profile 无效（`invalid_profile_count=4`）；反之 `status=partial` + `summary.correctness_passed=true` 按平台口径是**完成**（`S5-REPORT-BENCH` 只是 warning），不要为把状态刷成 `passed` 去动 benchmark。
- **一次 launch 多个 kernel 的 op（如 Decode 的 project+step）必然在 msprof 下报 `unfiltered capture contains N distinct ops`**：`tileops/benchmark/msprof.py` 的 kernel-name 解析链（Op 级 -> Kernel 级 -> env -> 从 `JitKernel_NPU` 派生）在多 kernel op 上全部落空返回 `None`，且 `--kernel-name` 只接受**单个**名字，即使给其中一个 kernel 声明名字也会漏掉另一个的时长。看到该报文先查「这个 op 是不是多 kernel」，而不是怀疑采集环境；正确做法是 harness 支持多名字过滤或按 launch 采集。
- **集成前逐字核对三件事**（本次靠它 0 attempt 过关）：工厂返回是一级还是二级、prim_func 张量声明的是 `d` 还是 `d_padded`（决定 wrapper 要不要 pad/裁回）、dtype 字符串；三者任一错都只会在 report 期或 `forward` 首次调用时暴露。
- **GPU 时代残留的模块级常量（`ALIGNMENT` 等）在 Stage 3 契约内移后必须从 wrapper 的 import 名单删掉**——集成脚本会把它当契约名生成聚合 import/`__all__`，否则集成 smoke 直接失败。
- **`status=partial` 的归因要看 `warnings` 的 op 前缀**：本任务 4 条无效记录全属 `EngramDecodeFwdOp`，本算子 3/3 有效；报告里必须把「整轮状态」和「本算子状态」分开写，否则下游会把别的 op 的缺口记到本算子头上。
