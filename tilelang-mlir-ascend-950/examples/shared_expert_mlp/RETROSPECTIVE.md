### Transferable Lessons（可迁移教训）

- A migrated wrapper that decomposes one op into several TileLang children must translate **every** child's build-time precondition itself (M/N tile exactness, `block_k | k`, split-K slice legality); the CPU-side defaults copied from the GPU reference are prefill-shaped and will raise on the decode band (`T=1`, `T=32`) and on non-16-aligned widths.
- When a kernel refuses a K tail (`k % block_k != 0`), the migration-side answer is host work, not a kernel change: first walk a `64/32/16` tile ladder, and only if no lane divides `k` zero-pad the contraction — zeros are exact, so the padding changes tile geometry only.
- Split-K decisions must be made against the **effective** tile (`min(block_m, ceil16(m))`), and the very same split count must construct the reduce kernel; changing the split silently changes the GEMM's output shape (`[split_k, m, n]` fp32 vs `[m, n]` dtype).
- For a decomposed op, treat `benchmarks` output as per-launch kernel numbers until someone declares an op-level `msprof_kernel_name`: a `partial` report with `invalid_profile_count == case_count` and reason "2 distinct ops" is a reporting-attribution gap, not a performance defect.
- Before blaming the kernel for a failing case, check whether the failure is a validation-message contract in `tileops/ops/` or `tests/ops/`: two "rejects invalid tensor" parametrizations can be mutually contradictory (square shapes make it ambiguous which tensor is wrong), in which case only the Stage 0 owner can fix it and Stage 5 must report, not patch.
